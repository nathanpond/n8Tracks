# n8Tracks

Product requirements live in `docs/PRD.md`.

## n8SDLC project

This project is managed by the n8SDLC workflow (GitHub Issues = the plan; `/n8-stat` shows where things stand). If a change made in this session deviates from what planned issues assume — different library, provider, architecture, dropped/added scope, or amending a declared invariant below — do two things before finishing:
1. Append an `## Ad-hoc` entry to `.n8/decisions.md` (format documented in that file's header) naming the change, the why, and the milestones/issues likely affected.
2. Tell the user which future milestones may now have stale plans and suggest running `/n8-replan`.

Background work (shells, monitors, background subagents) follows `reference/background.md` in the n8SDLC plugin. Every launch is bounded and announced with what it's for and when it should finish. Overdue work is checked, not waited on. A turn never ends with work still running unless the reply names it. `/n8-subs` lists everything live.

Separately: if a `/n8-*` skill's own instructions failed, misled you, or were silent on something this session, tell the user and offer `/n8-feedback` — it packages the learning as an issue on the plugin repo, stripped of project specifics, and sends nothing until the user has reviewed the exact text.

### Invariants

No story may breach these without an explicit conversation with the user. Changing one is plan drift: log it as an `## Ad-hoc` entry and run `/n8-replan`. All are **test-enforced**; the epic that owns each guard is named.

1. **Version immutability.** A Version's creation inputs and lineage sources cannot change once a Generation is attached, through any path (UI, API, import, MCP). Guard: epic #7. guard: #69 (planned); extended by #122, #140 (merged), and on the MCP path by #254 (planned)
2. **Media mount is never written (V1).** n8Tracks never writes, renames, moves, or deletes under `/media`, and no path input escapes the mount root. Expected to change in V2. Guard: epic #16. guard: #205 (merged), strengthened by #384, #386, #387; extended to imported audio paths by #259 (planned). `MediaMountGuardTests` covers every `IMediaMount` operation on a tree made read-only with `chmod`, links that escape, stay inside, or cycle, a cataloged file swapped for an escaping link, traversal refused by the resolver, an open of a cataloged file that has vanished (it fails and creates nothing), the reader handing out a read-only stream with no path (never its `FileStream`), and API inputs named like a path. `MediaMountAccessTests` is a source scan of `src/` that reads each file whole, so a call split across lines is seen: only `MediaMountReader` names the media setting besides the options loader (which also refuses a data or backup folder inside the media folder), the backup `IsInside` comparisons, and `MediaEndpoints`, which answers the configured path as text for the Media page; file-system APIs appear only in listed files, a `System.IO` file-system type named in full (an alias, a `using static`) counting; the reader has no write, move, delete, or attribute call, every `FileStream` it opens names `FileAccess.Read`, and it names `FileMode`, `FileAccess`, `FileShare`, and `FileOptions` only as their read members (no cast, parse, or arithmetic); nothing under `src/` uses P/Invoke, native libraries, function pointers, or `dynamic`; only health and setup probe through `IMediaMount`; and the guard of "no endpoint takes a path" is structural: every call that hands `IMediaMount` a path is a listed one with its argument (the content service passes only the stored path of a record found by ID, the scan only paths it listed), and the types built with the mount take no text from their callers. At startup, `docker/entrypoint.sh` refuses, before any `chown`, a `/data` or `/backup` that is the media folder, lies inside it, or holds it (by device and inode, real path, and `/proc/self/mountinfo`), and the app refuses a data or backup folder inside the media folder (real path, and the mount table on Linux); `scripts/smoke-docker.sh` scans a `:ro` container mount and starts containers with overlapping mounts. Neither covers: writes by other software sharing the mount; a mount the operator made writable and then pointed elsewhere; the window between the real-path check and the open, which only Linux narrows by reading `/proc/self/fd` after the open and other systems leave open; hard links, which have no target to check; file systems mounted inside the mount; a link spelled in a different case on a case-insensitive file system, which is refused as escaping rather than followed; a path to the mount that reaches code without naming the setting (record deconstruction, reflection, a hand-typed path); a library given a path that opens files itself; a `FileMode` or `FileAccess` value held in a variable and changed there inside the reader, which only the vanished-file runtime test stands behind; reflection into the stream the reader hands out; the read-only `chmod` case under a privileged process, where the container case is the proof; the shell code and image build (`docker/entrypoint.sh`, the `docker/n8tracks` wrapper, the `Dockerfile`), which no source scan reads and only the smoke test exercises; an overlap the startup checks cannot see, such as two network shares of one remote folder, or a mount added to a running container; and whether `NoEndpointTakesAPath`, which still checks input names only, sees a path-like input that never reaches the mount
3. **Imports never silently overwrite.** Suno import and portable import never change existing catalog data without an explicit user choice. The one exception is Suno's own state, which may follow Suno without a choice in exactly two cases: #154 completes a Generation the user just created (an observed Create, never complete, and not decided by a reviewed export), in its clip columns and raw clip only; and #314 moves a Generation still generating to Suno's final status (complete or error) at a commit whatever its choice, Skip included, in that status column only, never changing a final status. Portable import has no exception. Guard: epics #14, #22. guard: #140 (merged) for Suno import (`ImportNeverOverwritesGuardTests`: every catalog row before and after a commit, only rows a confirmed choice names may change; the #314 exception by the rule `TakesSunosFinalStatus`, the #154 exception by the completion rule `CompletionUnexplained`, each with a test that fails when it is overstepped; staging by `SunoExportStagingGuardTests`); #263 (planned) for portable import
4. **Suno is never mutated destructively (V1).** Nothing deletes or trashes Suno content, and the extension never clicks Create, Publish, or Delete on its own. Expected to change in V2. Guard: epic #15. guard: #133 (merged)
5. **One business-rule layer.** The web UI, API, and extension go through one application-service layer. The MCP gateway calls only the REST API and holds no business logic or catalog data. Guard: epics #4, #21. guard: #25, #33 (merged); the gateway half is extended by #254 (planned)
6. **Sensitive data is never logged.** Credentials, tokens, cookies, lyrics, prompts, and raw provider payloads are redacted from logs and diagnostics by default. Guard: epic #4. guard: #27 (merged)
7. **No destructive MCP capability (V1).** No MCP tool or scope can delete records, manage credentials, touch the filesystem, or drive Suno. Guard: epic #21. guard: #254 (planned)
8. **Warnings are errors.** Analyzers and linters stay on in the backend, frontend, extension, and gateway; any suppression carries a one-line rationale. Guard: epic #5. guard: two checks in the `guards` job of `.github/workflows/ci.yml` (merged). `scripts/check-suppressions.sh` reads configuration: tracked text and XML, for the listed forms of a suppression without a rationale and of a weakened setting (tested by `scripts/tests/check-suppressions/run.sh`; #43, #44, #194, #199). `scripts/check-canaries.sh` tests the effect: in a temporary copy, a known-bad file in every .NET project must fail the build with CS8618 and CA2200 as errors, and known-bad files in `web/`, `extension/`, and `e2e/` must fail `npm run lint` and `npm run typecheck` with the marked rules and error codes (tested by `scripts/tests/check-canaries/run.sh`; #199). Neither covers: a suppression scoped to files the canary is not in and written in a form the scanner does not list, a rule or diagnostic that has no canary switched off by a route the scanner does not read (a package, a computed configuration), a workflow or Dockerfile command line that takes its arguments or environment from outside the repository, a setting name assembled at run time, whether CI runs the gate and over which projects, which ESLint rule sets apply to which files (#197), or whether a rationale is true; the full list is under "Not covered by either check" in `scripts/check-suppressions.py`
