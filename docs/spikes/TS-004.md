# TS-004: how Suno delivers each download format

**Run:** 2026-10-05, in the maintainer's signed-in browser (plan: Premier), in the same session as TS-003, with the same in-page recorder (addresses, bodies, timings; no headers). The agent opened the Download dialog on a spike clip without unlocking it. The maintainer then downloaded WAV, MP3, and M4A of one song of their own choosing, so the one metered unlock went on a song they wanted. A throwaway unpacked extension (kept in the ignored `docs/.notes/suno/`, permissions `downloads` and the two audio hosts) tested saving under a chosen name; the files it saved were deleted afterwards. Nothing was created, published, deleted, or trashed. Fixtures: `extension/fixtures/suno/` (`download-*`, `billing-info.download-excerpt…`, `page.download-dialog.html`, `page.clip-download-menu.html`).

## The download dialog

A clip's **More options › Download** has no submenu. It opens a dialog titled "Download '<title>'" with M4A (selected by default), MP3, WAV, "MP4 video asset", and "Stems & MIDI" (with Manage). A single button reads **Unlock & Download**. Under it the dialog shows the plan (Premier), the plan's **downloads** allowance (60), and when the allowance refreshes. Opening the dialog requests only `GET /api/billing/info/`, whose `download_usage` holds `current_period_downloads_used`, `current_period_downloads_limit` (60), and `additional_download_remaining`. Its `download_credit_packs` sells extra downloads ($2.99 for 1 up to $29.90 for 10). Every clip in the feed carries `is_download_unlocked` (false on all clips seen before the run).

The page saved the files as `<title>.wav`, `<title>.mp3`, and `<title>.m4a`. Video and Stems & MIDI are out of scope and were recorded by name only.

### Saving under a chosen name

The throwaway extension passed each address to `chrome.downloads.download({ url, filename: "n8tracks-ts004/<chosen>.<ext>" })`. Each download **completed**, but **under the address's own name** (`<id>.wav`, `<id>_lyrics.mp3`), not the chosen one. Chrome also renamed both M4A files to **`.mp4`**, following the `audio/mp4` content type. The cause was not established. The usual one is another installed extension that renames downloads (`downloads.onDeterminingFilename`); the maintainer's browser runs several. Every name still contained the clip's Suno ID.

### Limits and failures

- Not probed: one clip was unlocked, no attempt was made to hit a rate limit, and only one file was prepared at a time.
- Failure was not observed. A failed preparation presumably answers without `status: "ready"`; it is not determined what that looks like.
- An exhausted allowance was not observed. `download_usage` shows the remaining count before any click.
- Plans other than Premier, and clips not owned by the user, were not determined.

## Decision

Per format:

- **WAV, MP3, M4A: obtained by operating the page and observing, then downloaded by address without credentials.** The adapter opens the clip's Download dialog, chooses the format, and clicks the dialog's button. It reads the `download_url` from the page's own `GET /api/download/clip/<id>?format=…` response, and passes that address to the browser's downloads interface. Nothing is added to the request.
  - For a clip that is **not yet unlocked**, the button is Unlock & Download and spends one of the user's plan downloads. **The maintainer has allowed this (2026-10-05) under one condition.** Before a run starts, the panel shows how many unlocks the run will use and how many remain this period (from `download_usage`), and the run starts only after the user confirms. A run never needs more unlocks than remain, and the extension never buys download packs.
  - A clip with `is_download_unlocked: true` costs nothing and needs no confirmation.
  - This reverses the plan's rule that a step spending credits makes a format "not automatable". It is logged as an Ad-hoc entry in `.n8/decisions.md`.
- **Playback stream (m4a-opus): downloaded by address without credentials, no page operation.** The address is `media_urls[0].url` in the clip data. It is offered as a fourth format, "M4A (streaming quality)", labelled as lower quality. It needs no unlock.
- **Not automatable:** none.

### Changes this forces on the stories

- **#215 (pick clips and formats).**
  - Formats are WAV, MP3, M4A, and M4A (streaming quality).
  - Each clip shows whether it is already unlocked on Suno.
  - The summary shows how many unlocks the run would use against the remaining allowance, read from the page's `GET /api/billing/info/`.
  - Start is refused when the run needs more unlocks than remain.
- **#216 (download the selected files).**
  - Per format, the steps are as above. Unlocks happen only after the user confirms the count in the summary.
  - Preparation waits up to 30 s per file (the observed 5.4 s for WAV, with a margin; the sample is small).
  - A signed address expires after one hour, so a file is prepared just before it is downloaded and never queued with an old address.
  - After each download the extension reads the final file name from the downloads interface. If the browser or another extension did not apply the chosen name, the file is reported as saved under a different name. Its Suno ID is still in the name the browser chose (`<id>.wav`, `<id>_lyrics.mp3`), and #206's matcher must also recognise a bare Suno UUID in a file name. A `.mp4` extension on an M4A must be accepted too.
  - Two audio hosts are listed: `suno-data-uploads.s3.amazonaws.com` and `d2lwuy8qc234o3.cloudfront.net`.
- **#222 (record downloads).** Format values gain `m4a-stream`, so a report is refused unless the format is `wav`, `mp3`, `m4a`, or `m4a-stream`. A report also records whether the run spent a Suno unlock for the clip.

`docs/suno-integration.md` is amended in this change with the second exception to observing, plus the unlock rule and the two audio hosts.
