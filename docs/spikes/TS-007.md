# TS-007: Suno's fetch calls and the Library pager

**Run:** 2026-10-08, in the maintainer's signed-in browser, after a sync stopped live with "step 'Read the library' expected a page of the library feed within 20 seconds of opening the page". Page HTML (direct load of `/me` with scripts, Library › Songs on pages 1 and 2, the Trash, a playlist) and the page's own requests and responses (`{page?, url, method, request, status, response}`). Nothing was created, published, deleted, trashed, or restored. Raw captures stay in the ignored `docs/.notes/suno/ts-007/`. Fixtures: `extension/fixtures/suno/page.library-songs-page-1.html`, `page.library-songs-page-2.html`, `feed-v3.workspace-create-wid.request.json`, and `feed-v3-offset.response.json`, sanitized as TS-005's were (placeholder IDs from `…000000000401`).

## Root cause: the body is on a `Request`

- Suno's page now calls `fetch(request, { headers })`. The first argument is a `Request` carrying the method and the JSON body; `init` holds only `headers`, so `init.body` and `init.method` are undefined.
- The observer (`extension/src/page/observe.ts`) passed `init?.body` on, so `observedRequestOf` read no body, the forwarded `request.filters` was null, and the library reader's `LIBRARY.accepts` (which needs a `user` filter) turned down every page. A workspace feed (matched by its `workspace` filter) failed the same way. The method was already read from the `Request` when `init` has none.
- Captures 01–07 have a null request for that reason; 11–20 were recorded after the recorder read the `Request` and have full bodies.
- The user's Create (`/api/generate/v2-web/`, #149's Observed Create) was not captured, but goes through the same wrapper, so its `submitted` values were very likely lost the same way.

## The pager

- Library › Songs (`/me`) no longer loads more on scroll. Below the list is a pager: `<div><span>Page</span><button disabled>‹</button><input placeholder="#" value="1"><button>›</button></div>`. Both buttons are `type="button"`, have no accessible name, and hold only an svg chevron.
- On page 2 the box reads 2 (its placeholder too), ‹ is enabled, a third icon-only button (an × icon) follows ›, and "Showing one page of 20 songs" sits above the pager.
- Pressing › sends `POST /api/feed/v3/offset` (`{ offset, filters }` → `{ offset, clip_id }`), then the usual `POST /api/feed/v3` (`{ cursor, limit: 20, filters }` → `{ clips[20], next_cursor, has_more }`). The offset answer is not a page of the list; the observer matches paths exactly, so `/api/feed/v3/offset` is not taken for `/api/feed/v3`.
- The Trash and the playlist page have no pager (no "Page" label in their snapshots); they still load more on scroll, as TS-003 found.

## The first page on a direct load

- Twice, a direct load or refresh of `/me` made no `POST /api/feed/v3` within 15 seconds; the page showed songs from its cache. Another direct load did make the request. A reader waiting for "the first page within 20 seconds of opening the page" cannot count on it.
- `/me/workspaces` loaded directly made no `GET /api/project/me`; clicking the Workspaces tab inside Library did. The panel's workspace and playlist choices are filled from those responses, so they depend on the user opening the tab.

## Workspaces on `/create?wid=`

- Opening a workspace from Library › Workspaces now goes to `/create?wid=<workspace ID>`. There the page asks for `GET /api/project/<id>`, `GET /api/project/<id>/pinned-clips` (both new to us), and `POST /api/feed/v3` with `filters.workspace = { presence: "True", workspaceId }` and `disliked: "False"` (TS-003's workspace request had no `disliked`). The second page came with a cursor while the page loaded, so whether this feed pages by scroll or by a pager was not seen; there is no snapshot of it.
- The sync does not read a workspace on its own page: a workspace-scoped sync reads the whole library feed on `/me` (the `user` filter) and keeps the clips whose `project.id` is chosen (`libraryReader.ts`). `/create?wid=` is reached only by the Create workspace selector (#145), which reads no feed. Nothing there changed for the reader.

## Response shapes against TS-003/TS-004

- `GET /api/clips/trashed_v2` and `GET /api/playlist/me`: unchanged.
- `GET /api/project/me`: projects carry a new `is_pinned_in_library`.
- `POST /api/feed/v3`: unchanged at the top (`clips`, `next_cursor`, `has_more`); clips carry a new `caption`. The differences deeper in `metadata` follow the kind of clip, not a change of shape.
- `POST /api/unified/feed` for a playlist's songs (`/playlist/liked`, `feed_id: "liked_songs"`): `feed.next_cursor` is present (TS-003's 8-song playlist had none); `feed.feed_container_id`, `feed_metadata.cover_image_grid`, and `items[].added_at` were absent; items may carry `persona`, `video_cover_url`, and more `metadata`. The reader reads `feed.items[].content_item` and ends by song count, which is unchanged.
- New: on `/me/playlists` the page also sends `POST /api/unified/feed` with `feed_id: "library_playlists"` (`page_size: 12`, `request_metadata: { term, library_scope }`, `customization: { include_synthetic }`). The reader does not take it: a playlist leg accepts only its own `generic_playlist:<id>` feed.

## Not captured

- The user's Create request since the change (assumed to be a `Request` too).
- The pager on the last page (whether › is disabled there). The reader stops at `has_more: false` before asking.
- Whether going back from page 2 to page 1 asks for page 1 again or shows it from cache.
- Whether the workspace list (`/me/workspaces`) and a workspace's feed on `/create?wid=` page by scroll or by a pager.

## Decisions

- **TS-007-1. The observer reads a `Request`'s body from a clone** taken before the page's request goes out (a body can be read once, and a used one cannot be cloned). `init.body` is used when given, as `fetch` itself does; the method is `init.method`, else the `Request`'s. A body already used, or one that cannot be read, is read as none. The page gets its own `Request`, `init`, and response unchanged.
- **TS-007-2. `load-more` presses the pager's › where there is a pager, and scrolls where there is none.** The › is found by structure only: the one visible `span` reading exactly "Page", whose parent holds, in order, that span, a button, an `input` with a placeholder, a button, and then only buttons, every one of them unnamed, without text, and showing an icon. The › is the button after the input. Any other shape stops the step with nothing pressed. The press goes through the click primitive, so the forbidden-control matcher is asked as for any other control.
- **TS-007-3. A first page that does not come is handled by the existing reopen path** (`ReadStop.reopen`: the page is opened again, up to `PAGE_RETRIES` times). Going to page 2 and back was not chosen: page 2's response would arrive first, and whether page 1 is asked for again was not seen. Clicking the Library tab was not chosen: the adapter reaches pages by address, never by pressing a link. The extension still sends no request of its own. (The workspace list became the one exception on 2026-10-11: TS-007-6.)
- **TS-007-4. The panel says to open the tab, not to refresh**, when Suno has listed no workspaces or playlists: "open Library on Suno, then click the Workspaces tab (refreshing the page does not load the list)", and the same for Playlists.
- `ADAPTER_VERSION` 16.
- **TS-007-5. A page seen before is skipped, not a stop.** Seen live on 2026-10-11, after the sync stopped with "Suno sent a page of the library feed again": opening Library › Songs asks for page 1 and then fetches page 2 ahead (two `POST /api/feed/v3`, the second with page 1's `next_cursor`). The first › sends `POST /api/feed/v3/offset` (`offset` 19) and then asks for page 2 again, with the same cursor and the same clips. Later presses ask only for the new page (`offset` 39, then page 3), with nothing fetched ahead. The reader skips a page whose cursor it has read and does not press › for it. It stops only after `PAGE_RETRIES + 1` repeats in a row with no new page between them, so a page Suno keeps sending still ends the read. `ADAPTER_VERSION` 17.
- **TS-007-6. The workspace list is reached by pressing Library's Workspaces tab** (#421, owner decision, 2026-10-11). This reverses TS-007-3's "the adapter reaches pages by address, never by pressing a link" for this one case. Seen live on 2026-10-11: a direct load of `/me/workspaces` shows the list with no `GET /api/project/me` (the only API calls were rum, nudges, and share stats), and the first workspace sync stopped at "Read the workspace list". Loading `/me` (Library › Songs) and pressing the Workspaces tab does send `GET /api/project/me?page=…&sort=…&show_trashed=…&exclude_shared=…`, answered in the shape the reader already takes (`projects`, `current_page`, `num_total_results`); the tab moves the page to `/me/workspaces` without loading a new document. The sync's workspace-list leg therefore opens `/me` and runs `open-workspace-list`: the tab is found by role (`tab`), its exact name "Workspaces", and the path its own `href` names (`/me/workspaces`), as in `page.library-list.html` and `page.library-songs-page-1.html`. None, or more than one, stops the step with nothing pressed. The press goes through the click primitive, so the forbidden-control matcher is asked; a tab only changes what Library shows. The reader then waits for the list as before, and when none comes within 20 seconds Library is opened again (TS-007-3's path, at most `PAGE_RETRIES` times). The extension still sends Suno no request of its own. `ADAPTER_VERSION` 19 (with #422).
- **TS-007-7. A workspace sync reads each workspace's own feed on `/create?wid=`** (#422, owner request, 2026-10-11). Captured live on 2026-10-11 (a workspace of 45 clips): opening a workspace goes to `/create?wid=<id>`, which asks for `GET /api/project/<id>`, `GET /api/project/<id>/pinned-clips`, and `POST /api/feed/v3` with `{ cursor: null, limit: 20, filters: { disliked, trashed, fromStudioProject, stem, stemComplement, workspace: { presence: "True", workspaceId } } }`, answered `{ clips, next_cursor, has_more }`. Scrolling the song list (the right-hand pane; Suno's Create form, with its Create button, is on the left) asks for the next page with the previous `next_cursor`, until `has_more: false` (pages of 20, 20, 5). There is no Library pager there; the header's small ‹ 1 › control has no "Page" label. This answers the "Not captured" question above for a workspace's feed (by scroll); the workspace list's own paging is still not seen. A workspace sync's legs are now the workspace list, then one leg per chosen workspace on `/create?wid=<id>`, then the Trash when asked (#420). Each leg takes only feed answers whose `filters.workspace.workspaceId` is its workspace, and `load-more` there scrolls only the song list's own pane (the nearest element around the `rowgroup` that scrolls), never presses a pager, and leaves the Create form's pane alone. - **TS-007-8. Lyrics go into Lexical by select-all and one paste.** Seen live on 2026-10-11: Generate on Suno filled Advanced lyrics as one line. In Suno's lyrics editor, `execCommand('insertParagraph')`, `insertLineBreak` and `insertText('\n')` all join the lines into one paragraph. A DOM select-all followed by `delete` leaves text behind once there is more than one paragraph, because Lexical keeps its own selection. These work: the select-all shortcut (a `keydown` of mod+A, ⌘ on Apple platforms and Ctrl elsewhere) followed by a `paste` of the whole text as `text/plain`. Each line becomes a paragraph, and blank lines and leading spaces are kept. Select-all followed by a Backspace `keydown` empties the editor. `typeText` now does this. It falls back to the line-by-line editing commands only where nothing cancels the paste or the key. No Enter key is ever sent. On a freshly loaded page Lexical has no selection until the browser's `selectionchange`, a task after focus, and it cancels a paste that arrives before then but inserts nothing (seen live: the first build left the lyrics empty). So `typeText` waits 50 ms after focus, and 50 ms after the paste or key for the editor to apply it. `ADAPTER_VERSION` 20.
- **TS-007-9. A slider is stepped one key at a time, read again after each** (#427). Seen live on 2026-10-11, after Generate on Suno reported Style Influence "Differs: expected 85, found 51": Suno's `role=slider` divs in More Options (Weirdness, Style Influence, Variety; no `input[type=range]`) apply an arrow key a task after it, from the value they had when the key came. Five keydown/keyup pairs sent back to back moved 50 to 51; with a task (`setTimeout 0`) after each, every key counted (52, 53, 54, 55). The old stepping read `aria-valuenow` straight after each key, saw no change, and stopped after one. Moving a slider is now its own primitive, `Page.slide` (async; `set` refuses a slider): after each key it waits `SLIDER_KEY_SETTLE_MS` (10 ms) on the page's clock and reads the slider again, and keeps reading until it changes or `SLIDER_KEY_WAIT_MS` (400 ms; one key was seen to show about 300 ms after a burst) has passed. It stops at the value, when a key changes nothing in that time (a slider at its end, or one that ignores keys), or after a key passes the value (Duration's 5-second steps still end on the nearer step); at most `MAX_KEY_STEPS` keys. A range input, where there is one, is still set directly. No Enter is sent. A test slider that applies keys a task later reaches 85 from 50 (and the Songs fillers set Weirdness, Style Influence, and Variety on it), while the same keys sent back to back leave it at 51.

The forbidden-control matcher recognises the "Model" dialog: it allows Close and its rows (`pressesRows`), refuses a row whose name or text starts with Create, Publish, Delete, Trash, or Remove (so "Create Custom Model" is never pressed), and takes a `grid` or `rowgroup` as a container, as it does a tab list.
