# TS-001: Suno generation correlation

**Run:** 2026-10-03, in the maintainer's signed-in browser, driven through Claude in Chrome. The maintainer clicked Create twice, about 18 seconds apart, with the same Simple-mode prompt. An in-page recorder captured Suno's own requests and responses (addresses, bodies, timings; no headers). Sanitized examples are in `extension/fixtures/suno/`.

## Findings

| Question from the PRD | Answer | Evidence |
|---|---|---|
| Does a request or batch identifier exist in the DOM, page state, network traffic, or exported provider data? | **Yes, in network traffic, at Create time only.** The response to `POST /api/generate/v2-web/` has a top-level `id` for the request, a `batch_size`, and the `clips` it produced. | Two Create clicks returned two different top-level IDs, each with `batch_size: 2` and two clips. |
| Do output records share any reliable creation identifier? | **No shared ID on the clip records.** Neither the clips in the Create response nor the clips later returned by the library feed carry the request ID. | Searched every captured response for both request IDs: they appear only in the two Create responses. The feed returned all four clips without them. |
| Is `batch_index` stable, what does it mean, and can it be combined with another field? | **Stable; it is the clip's position within its Create request (0, 1).** It is present in the Create response and unchanged in the feed before and after completion. Combined with `created_at` it identifies the pair. | Each request's clips had `batch_index` 0 and 1; the same values came back from the feed while streaming and when complete. |
| What event does the available timestamp represent? | **Submission.** `created_at` is set when the request is accepted and does not change when the clip finishes. | A clip's `created_at` was identical while `submitted`, `streaming`, and `complete`. The request-level `created_at` was 44 ms earlier than its clips'. |
| Do two outputs of one Create action get equal or different timestamps? | **Equal or within about a millisecond.** | First request: both clips `…53.697Z`. Second request: `…11.257Z` and `…11.258Z`. The two requests were 17.6 seconds apart. |
| Can the extension observe the Create action and associate the resulting Suno IDs without invoking it? | **Yes.** A script running in the page can read the Create response when the user clicks Create, and it contains the request ID and both clip IDs. | This spike did exactly that with a wrapper around the page's `fetch`. |
| What happens when one output succeeds and another fails or arrives later? | **Not determined.** No failure occurred. Each clip has its own `status` (`submitted`, `streaming`, `complete`), so outputs do progress independently. | Both clips of the first request were `streaming` while both of the second were still `submitted`. |
| Behaviour across page refreshes, navigation, multiple tabs, and concurrent Create actions? | **Concurrent requests are distinguishable** (separate request IDs). **A refresh or another tab loses the request ID**, because it exists only in the Create response received by the tab that made the request. After that, only `created_at` plus `batch_index` remain. | Inferred from the data above; a refresh and a second tab were not separately exercised. |

## Other observations

- **The Create response echoes the submitted inputs.** Its `metadata` holds the prompt, `make_instrumental`, `control_sliders` (for example `aug_creativity: 4`, which matched the form's Variety at Max), `task`, and more. This is the "effective form state at the generation boundary" the PRD asks for, without reading the form.
- **Completed clips gain fields:** `duration`, `tags`, `min_bpm`/`max_bpm`/`avg_bpm`, `key`, `has_stem`, `media_urls`, `image_url`, and others.
- **Each clip in the feed carries its workspace** as `project` (`id`, `name`, `description`, `is_trashed`, `is_public`), so the workspace ID comes with the clip.
- **`is_trashed` and `is_hidden`** are on every clip.
- **The model shown and the model reported differ.** The form had `v6-mini` selected; the clips report `major_model_version: "v6"` and `model_name: "chirp-goose"`. n8Tracks must store what Suno returns, not the form label.
- **`audio_url` on a completed clip was a placeholder** (`…/api/forbidden`); the playable file was under `media_urls`.
- **`action_config`** lists the actions available on a clip (`remix_extend`, `remix_cover`, `remix_reuse_style`, `download_song`, and others), with `disabled` flags. Useful for TS-002.
- **Status updates did not arrive by polling the feed.** Only one feed request was seen while four clips progressed, so progress reaches the page some other way (not captured). The extension should re-read the feed, not depend on that channel.
- The Create request body was not captured (it was not sent as a plain string); the response metadata covers what was submitted.

## Decision

Generation Events are correlated in two tiers, and the data model allows no correlation at all:

1. **Observed (high confidence).** When the extension is present in the tab where the user clicks Create, it reads the Create response and records the request `id`, `batch_size`, and the clip IDs. Correlation source: provider request ID.
2. **Inferred (medium confidence).** For clips first seen later, during a library sync, clips are grouped when they share a workspace, have `created_at` within one second of each other, and have distinct `batch_index` values starting at 0. Correlation source: timestamp and batch index. This is offered as a proposed grouping the user can accept or change, never applied silently, because the PRD forbids treating timestamp proximity alone as authoritative.
3. **None.** A clip with no observed or accepted grouping has no Generation Event. Ownership by a Song and Version never depends on it.

## Degraded and manual fallbacks

- If the page's Create request or response changes shape, tier 1 stops and the extension reports the failing step; tier 2 still works from the feed.
- If `batch_index` or `created_at` disappears from the feed, no grouping is proposed and Generations are imported without events.
- Partial failure of a batch was not observed; until it is, a batch whose clips do not all appear is recorded with the clips that did.
