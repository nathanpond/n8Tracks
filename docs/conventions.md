# Project conventions

Shared build conventions the planned stories refer to as "the M2 conventions" or "the project conventions". A story's own acceptance criteria and discretion lines take precedence where they differ.

- API: versioned under `/api/v1`, JSON in camelCase, IDs are UUIDv7 strings. Errors are Problem Details (`application/problem+json`) with a stable machine-readable `code`.
- Concurrency: every editable record has an integer `revision`, starting at 1 and incremented on each successful write. A write sends the revision it read (`If-Match: "<revision>"`). A stale write returns 409 with `code: revision_conflict` and `current`, the full current record; the client works out which fields differ from what it loaded. `If-Match` is a quoted integer; anything else is 400 `invalid_revision`. A write without a revision returns 428.
- Authentication: the web UI uses a cookie session; unsafe methods from the browser also require an anti-forgery header. Non-browser clients use `Authorization: Bearer <token>`. Until the sign-in story lands, endpoints are open on the milestone branch.
- Authorization: every `/api/v1` endpoint declares the scope it needs. A cookie session holds every scope.
- Persistence: EF Core entities and snake_case tables in Infrastructure, application services in Application, endpoints in Api, per the layering guard. Each schema change is one EF Core migration.
- Frontend: Mantine components, React Router routes, data access through small hooks over `fetch` resolved against the page base URL. New screens are reachable from the sidebar of the signed-in shell.
- Tests each story adds: unit tests for domain rules, API integration tests (including the refusal cases), component tests for new UI states, and at least one end-to-end test in `e2e/` that walks the story's Demo and scans each visited state with the accessibility helper.
- Logging: any new field holding lyrics, styles, prompts, tokens, or passwords is added to the redaction policy's name list in the same story.
- Time: stored and returned as UTC ISO 8601; shown in the UI in the configured time zone.
- Suppressions: a warning switched off anywhere (`#pragma warning disable`, `#nullable disable`, `[SuppressMessage]`, `<NoWarn>`, `<WarningsNotAsErrors>`, `<MSBuildWarningsAsMessages>`, `<NuGetAuditSuppress>`, an `.editorconfig` severity below warning or analyzer exclusion, `eslint-disable`, `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`, an ESLint rule set to `off`) carries a one-line rationale of ten characters or more, or `scripts/check-suppressions.sh` fails CI. Where the rationale goes is described at the top of `scripts/check-suppressions.py`. A new EF Core migration needs a comment line above its `#nullable disable`; the generated `.Designer.cs` and snapshot files are exempt as long as they hold only what EF Core writes (one class, one `BuildModel` or `BuildTargetModel` method).
- Settings no comment can excuse: the same script fails CI when warnings-as-errors or strict checking is weakened, or when it meets something it cannot read. It scans every tracked file whatever its folder is called (`bin`, `obj`, `dist`, and `node_modules` included) and reads MSBuild files with an XML parser. `TreatWarningsAsErrors`, `EnableNETAnalyzers`, `EnforceCodeStyleInBuild`, `AnalysisLevel`, and `Nullable` are set once, unconditionally, in the root `Directory.Build.props` and declared nowhere else (`<Nullable>enable</Nullable>` may be repeated); there is no nested `Directory.Build.props` or `.targets`. Also failing: a tracked text file that is not UTF-8, a symbolic link, a submodule; an `<Import>` of anything but a tracked `.props`, `.targets`, or `*proj` file in the repository; an SDK other than the ones in use; any property or item that changes warning or analyzer behaviour (`RunAnalyzers`, `CodeAnalysisRuleSet`, `GlobalAnalyzerConfigFiles`, `Features`, `MSBuildTreatWarningsAsErrors`, `ImportDirectoryBuildProps`, `<Analyzer Remove>`, and the rest of the list in the script), or one set indirectly (`CreateProperty`, `Properties="..."`); generated-code markers outside EF Core's own files (`<auto-generated`, `*.g.cs`, `[GeneratedCode]`, `generated_code = true`); the same settings on a command line or as an environment variable in any workflow, Dockerfile (`ENV`, `ARG`), Compose file, shell or PowerShell script, `Makefile`, or `package.json` script (`-warnaserror-`, `-nowarn`, `NoWarn`, `TreatWarningsAsErrors=false`); in a workflow, `continue-on-error`, or a gate command whose failure is ignored (`|| true`, a pipe without `shell: bash`, `&&` before the last line of a step). JavaScript: the `lint` script of `web/`, `extension/`, and `e2e/` is exactly `eslint . --max-warnings 0` and the `typecheck` script exactly `tsc -b` (`tsc --noEmit` in `e2e/`); a `package.json` anywhere else with a `lint` script or an ESLint or TypeScript dependency fails until the guard is taught about it (`SCRIPT_PROJECTS` in the script); every `tsconfig*.json` there resolves to `strict: true` (set in the file or inherited through a local `extends`) with no strict-family flag or `noUncheckedIndexedAccess` set to `false`, and is one the `typecheck` script reads; an ESLint configuration ignores only build output, writes rule severities as literals, and imports no local file. The full list is at the top of `scripts/check-suppressions.py`. A new fixture case goes under `scripts/tests/check-suppressions/fixtures/` (layout in `run.sh`).
- What that script cannot catch (it reads tracked text and XML, nothing else): settings that come from outside the repository (a developer's shell, repository variables and secrets, a base image) or from a file created while the build runs; what a NuGet or npm package brings (build files, analyzer configuration, suppressors, a shared ESLint configuration, a replaced executable); a setting's name assembled at run time (shell variables, `eval`, GitHub expressions, MSBuild property functions, reflection); whether CI runs the gate at all and over which projects (a step removed or skipped, a job dropped from `ci`); failure handling inside shell scripts and Makefiles beyond `||`; which rule sets an ESLint configuration applies and to which files (#197: a `.js`, `.jsx`, `.mts`, or `.cts` source file gets no rules today); JavaScript outside the three projects that belongs to no `package.json`; language features that avoid a warning (`!`, `any`, `dynamic`); and whether a rationale is true. These are for review. The same list is in the script's header under "Not covered".
- Release rules: what a version tag publishes (which image tags, pre-release or not, latest or not) is decided only by `scripts/release-tags.sh`; a workflow runs it and reads its `key=value` output, and holds no tag logic of its own. The rules are at the top of the script. A change to them comes with a case under `scripts/tests/release-tags/fixtures/` (layout in `run.sh`), which runs in the `guards` job.
- Releasing: `.github/workflows/release.yml` publishes on a `v*` tag and holds no logic of its own. `scripts/published-tags.sh` lists what is already published, `scripts/publish-tags.sh --once "<version>"` creates the exact version tag (never moved once it exists; `--digest` reads where a tag points), and `scripts/release-github.sh` creates the GitHub release or adds what an existing one is missing, never replacing anything. A change to any of them comes with a check in `scripts/tests/publish-tags/run.sh` or `scripts/tests/release-github/run.sh` (stand-in `docker` and `gh` in each `fake-bin/`), both in the `guards` job. The `VERSION` file may hold a pre-release (`0.1.0-rc.1`); the gate must pass with one. The procedure is in `docs/releasing.md`.
- Edge publishing: what an edge build is called (short sha, version, `edge-<sha>` tag) is decided only by `scripts/edge-version.sh`, and published images are tagged only by `scripts/publish-tags.sh`, after both were pushed by digest; a workflow runs them and holds no naming or tagging logic of its own. The rules are at the top of each script. A change comes with a check in `scripts/tests/edge-version/run.sh` or `scripts/tests/publish-tags/run.sh` (the second runs against the stand-in `docker` and `gh` in its `fake-bin/`), both in the `guards` job. Both Dockerfiles stamp the version with `-p:InformationalVersion`, never `-p:Version`: an edge version is not always a valid NuGet version.
